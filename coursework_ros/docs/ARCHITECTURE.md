# Архітектура та межі компонентів

Проєкт має три чітко відокремлені режими.

| Режим | Джерело даних | Призначення |
|---|---|---|
| Онлайн AirSim | фізична сцена і RPC | основна демонстрація польоту, телеметрії та результату |
| JSON-відтворення | локальний `simulation.json` | перевірка і візуалізація готового запису без AirSim |
| ROS-заглушка | `guidance_checker` і `target_trajectory_node` | демонстрація контракту ROS-топіків без симулятора |

## Онлайн-потік

```text
scenarios/*.json
       │
       ▼
airsim_online_node (C++ / ROS 2) ⇄ AirSim RPC ⇄ WindowsNoEditor
       │                                      │
       │ UDP :8091                            │ головне вікно
       ▼                                      ▼
DASHBOARD_SERVER.ps1 ◀──── camera.json ── CAMERA_FEED.ps1
       │
       ▼
http://127.0.0.1:8080/
```

`airsim_online_node` читає стан AirSim, публікує ROS-повідомлення
`telemetry` (`nav_msgs/msg/Odometry`) та `selected_target`
(`geometry_msgs/msg/PointStamped`) і надсилає стислий JSON-стан UDP-пакетами
на локальний Windows-сервер.

`CAMERA_FEED.ps1` знаходить головне вікно готової сцени `MSBuild2018`,
захоплює його клієнтську область засобом Windows `PrintWindow` і оновлює
`web/live/camera.json`. Тому вебпанель показує той самий зовнішній ракурс і
службові написи, що й AirSim, без окремого регулятора камери.

`DASHBOARD_SERVER.ps1` об'єднує телеметрію, кадр і результати та обслуговує
одну HTML-сторінку. Завершені результати додаються до локального файла
`results/coursework_results.csv`.

## API локального сервера

| Метод і шлях | Результат |
|---|---|
| `GET /api/health` | стан локального сервера |
| `GET /api/state` | остання телеметрія; після 2 секунд без пакетів — offline |
| `GET /api/camera` | останній кадр головного вікна AirSim |
| `GET /api/results` | останні результати запусків |
| `POST /api/restart?curve_id=...&ammo=...` | запуск вибраного сценарію |
| `POST /api/stop` | зупинка активного ROS-запуску |
| `POST /api/close` | зупинка ROS, AirSim і локального сервера |

Сервер слухає лише `127.0.0.1` і не призначений для публічного доступу.

## Вхідні дані

У `scenarios/` містяться десять іменованих каталогів. Кожен має
`config.json`, `targets.json` та `ammo.json`; спільна
`ballistic_table.txt` лежить рівнем вище. Інтерфейс передає серверу тільки
дозволені ідентифікатори сценарію та набору параметрів.

`simulation.json` обробляється браузером локально. Для відтворення потрібен
непорожній масив `steps` із числовими `position.x` та `position.y`.

`windows/coursework.local.json` містить параметри конкретного ПК і не
комітиться: WSL-дистрибутив, користувача, контейнер, шлях проєкту, шлях до
сцени та необов'язкову адресу Windows-хоста.

## ROS-заглушка

`guidance_node` підписується на `/telemetry` і `/target`, а результат видає
в `/command`. `guidance_checker` подає контрольні повідомлення та перевіряє
отримання відповідей. Це окремий приклад інтеграції ROS 2; онлайн-вузол
AirSim не споживає `/command` цього демонстраційного вузла.

## Обґрунтування

Розділення C++/ROS, фізики AirSim, локального сервера та відображення дає
можливість незалежно перевіряти кожний шар. Стандартні ROS-повідомлення
дозволяють додавати зовнішні спостерігачі, UDP не блокує цикл симуляції, а
локальна вебпанель не потребує змін готової Unreal-сцени.
