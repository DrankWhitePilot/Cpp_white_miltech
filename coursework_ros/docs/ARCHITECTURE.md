# Архітектура та межі компонентів

У проєкті є **три різні демонстраційні режими**. Їх не можна називати одним
і тим самим тестом.

| Режим | Джерело руху | Що перевіряє |
|---|---|---|
| ROS-заглушка | `guidance_checker` і `target_trajectory_node` | API топіків та реакцію вузла без AirSim |
| Онлайн AirSim | фізична сцена через RPC | фактичну телеметрію, відображення й повний цикл демонстрації |
| JSON-відтворення | локальний `simulation.json` | перегляд офлайн-даних без фізики AirSim |

## Потік даних онлайн-режиму

`scenarios/{назва}/{config,targets,ammo}.json` →
`airsim_online_node` (C++/ROS 2, RPC-клієнт) ↔ AirSim Windows scene.

Паралельно C++ вузол публікує ROS-топіки `telemetry`
(`nav_msgs/msg/Odometry`) і `selected_target`
(`geometry_msgs/msg/PointStamped`), а короткий стан надсилає UDP на порт
8091 локального Windows-сервера. Сервер обслуговує панель через HTTP
`127.0.0.1:8080`, утримує обмежений запис фактичного шляху поточного запуску
та додає завершені результати до `results/coursework_results.csv`.
Панель показує стан, історію і геометричне порівняння шляхів. Вона не є
джерелом телеметрії AirSim.

## API локального сервера

| Метод і шлях | Результат |
|---|---|
| `GET /api/health` | доступність сервера |
| `GET /api/state` | останній отриманий стан; після 2 с без даних — offline |
| `GET /api/trace` | `schema`, `run_id`, `scenario`, масив `{t,x,y}` поточного запуску |
| `GET /api/results` | останні результати з локального CSV |
| `POST /api/restart?curve_id=...&ammo=...` | перезапуск вибраного сценарію |
| `POST /api/stop` | зупинка ROS-запуску |
| `POST /api/close` | зупинка ROS, сцени та локального сервера |

Сервер слухає тільки `127.0.0.1`. Це локальний навчальний інтерфейс, без
автентифікації та без гарантій для публічного мережевого розгортання.

## ROS-заглушка

`guidance_node` підписується на `/telemetry` (`nav_msgs/msg/Odometry`) та
`/target` (`geometry_msgs/msg/PointStamped`), публікує `/command`
(`geometry_msgs/msg/Twist`). За відсутності цілі видає нульову команду.
Чекер подає тестові повідомлення й підтверджує, що відповіді надходять.
Це окремий API-приклад; онлайн-вузол AirSim не споживає `/command` від
`guidance_node`.

## Формати й конфігурація

- У `scenarios/` десять іменованих каталогів. Кожен має `config.json`,
  `targets.json`, `ammo.json`. Спільна `ballistic_table.txt` лежить рівнем
  вище. Оригінальні структури вхідних даних збережено.
- `windows/coursework.local.json` містить тільки параметри **цього ПК**:
  WSL-дистрибутив, користувача, шлях проєкту, шлях Windows-сцени та, за
  потреби, адресу хоста. Його не слід комітити.
- `simulation.json` — локальний файл із масивом `steps`, доступний лише
  для відтворення. Він не використовується як запис телеметрії ДЗ11.
- CSV `hw11-telemetry-v1` — запис прийнятих пакетів телеметрії ДЗ11,
  створений параметром `--telemetry-log`. Для порівняння треба вручну
  підтвердити однакові початкові умови, систему координат і ділянку польоту.
  Формат та інструкція: [HW11_TELEMETRY.md](HW11_TELEMETRY.md).
- Запис `GET /api/trace` містить лише зростаючі часові позначки та кінцеві
  числові координати. Сервер зберігає до 5000 точок одного запуску.

## Обґрунтування і обмеження

Окремі C++/ROS, AirSim і відображення дозволяють незалежно перевіряти
складові. Стандартні ROS-повідомлення полегшують підключення зовнішніх
спостерігачів, а локальний HTTP/UDP інтерфейс відділяє візуалізацію від
симуляції. При цьому Windows-сцена й Linux-контейнер — дві залежні частини:
для іншої мережевої конфігурації може знадобитися `AirSimHost`.

Порівняння обчислює відстань **від кожної фактичної точки до найближчого
сегмента записаного шляху ДЗ11**: середнє, 95-й перцентиль і максимум. Воно не
синхронізує час, не перевіряє порядок проходження точок і не слугує
доказом фізичної тотожності моделей. Детальне ТЗ:
`TRAJECTORY_COMPARISON_SPEC.md`.
